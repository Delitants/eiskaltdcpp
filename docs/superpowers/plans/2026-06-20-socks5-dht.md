# SOCKS5 DHT Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:test-driven-development` for each task and `superpowers:verification-before-completion` before claiming completion.

**Goal:** Keep DHT functional through a SOCKS5 UDP relay even when proxying transfers forces the client into passive mode.

**Architecture:** Preserve the already implemented persistent SOCKS5 UDP association and packet framing. Decouple DHT startup from active TCP/UDP listener startup: passive proxy mode must not expose transfer/search listeners, but it may start DHT when a working UDP proxy endpoint exists. Keep direct-mode behavior unchanged.

**Tech Stack:** C++17, EiskaltDC++ connectivity/DHT core, SOCKS5 UDP ASSOCIATE, Catch2.

## Task 2: Decouple DHT startup from incoming listeners

- Modify: `dcpp/ConnectivityManager.h:55-75`
- Modify: `dcpp/ConnectivityManager.cpp:40-70`

- [ ] Add a testable `shouldStartDht()` policy that requires `USE_DHT`, then permits either direct networking or SOCKS5 with a valid UDP relay endpoint.
- [ ] Split `listen()` into two responsibilities:
  - `listenIncoming()` starts `ConnectionManager` and `SearchManager` only;
  - `startDht()` starts `dht::DHT` only when the policy allows it.
- [ ] In `startSocket()`, always disconnect old resources, start incoming listeners only when `ClientManager::isActive()`, then call `startDht()` independently.
- [ ] Do not start DHT for Shadowsocks TCP-only mode; the current Shadowsocks UDP support may be added to the policy only after its UDP integration tests pass.

- [ ] Keep `disconnect()` stopping incoming listeners and DHT.
